Realiza REQ-008 mediante ADR-012 a ADR-016. Es el cierre integrado de PRJ-003; no autoriza una publicación real ni una actualización del cliente.

## 6. Acceptance and Dependencies

- Para conectar sustitución/migraciones exige primitivas comprobadas de WP-006, WP-007 y WP-008. El esquema de resultados y guía pueden prepararse antes; no se activa una actualización parcial como si fuese operativa.
- Actualización e interrupción se ensayan en WP-010 sobre instalación completa sintética. AlreadyApplied no repite migraciones; UpdateFailedRecovered no se presenta como UpdateSucceeded; RecoveryRequired impide escrituras y otra actualización.
- Se verifica frontend anterior/backend nuevo y las parejas necesarias para recuperación. Se concilia la base existente de WP-004; publicar assets no demuestra que todas las pestañas los hayan recibido.
- AC-019, AC-020 y AC-110 exigen comprobar el flujo requerido de portal y escritura sintética. Si la ruta necesaria no está disponible, queda VerificationPending. Los resultados locales previos no se reutilizan como evidencia de la nueva cadena completa.
- La guía debe conservar identidad, configuración y dependencias, distinguir primera adopción de actualización habitual y recuperación, y explicar el nuevo login tras reiniciar API sin pedir recrear el usuario.
- TSK-034 queda pendiente de evaluar evidencia contra TMP/SQCA vigentes y de un revisor independiente para riesgo Critical, según estrategia local. No se declara aceptación de producto, despliegue remoto ni validación sobre el cliente por cerrar tareas de desarrollo.

### Conciliación del avance — 2026-10-16

La herramienta integrada, adaptación frontend y ensayos conservados justifican In Progress para TSK-031 a TSK-034; no se declara cierre de estas tareas.

- TSK-031: Actualizar.ps1 y Updater.ps1 integran Preflight, Apply, Finalize y Recover, fases persistentes y resultados diferenciados. El [informe de flujo](../../tests/artifacts/updates/flow-2026-10-11T16-17-18-593Z-e7738363/report.json) registra 13 variantes satisfactorias de alcance local: actualización, repetición AlreadyApplied, rechazo previo, verificación pendiente y recuperación coherente.
- TSK-032: el [informe de navegador](../../tests/artifacts/updates/browser-2026-10-11T16-04-06-825Z-4e6fdaf6/report.json) registra cuatro variantes satisfactorias con respuestas API sintéticas: formulario sin guardar, rechazo de mantenimiento, backend sin metadatos y contrato desconocido. No acredita todas las parejas reales frontend–API. El resumen registra compilación frontend correcta.
- TSK-033: comprobaciones de identidad y operaciones sintéticas integradas con API/PostgreSQL reales y proveedor de identidad/proxy simulados. Falta Keycloak real y ruta portal/Worker/Access/túnel autorizada; la simulación no cierra ese alcance.
- TSK-034: guía [USO.md](../../deploy/windows/update/USO.md), paquete de mantenimiento e informes disponibles según el [resumen local](../../tests/artifacts/updates/local-summary.json). Faltan evaluación formal de cobertura, servicios/reinicios Windows, revisión independiente y aceptación.

La entrega sigue declarando clientAccepted=false. WP-010/MS-004, origen cliente revisado, política de conservación compatible con identidad/migraciones reales y pruebas exigidas son condiciones abiertas para MS-003. No se autoriza publicación remota ni actualización del cliente.

### Ensayo de actualización en clon Hyper-V — 2026-10-20

El usuario aporta salida de `Ejecutar-Ensayo-HyperV-r10.ps1 -Action Apply` en la VM Windows 10 aislada: `LocalRehearsalSucceeded`, `verificationMode=LocalRehearsal`, con copia verificada/restaurada y autenticación local del propietario sintético reportada como correcta. El resumen sanitizado está en `tests/artifacts/updates/hyperv-update-success-r3-20261020.json`. Aporta evidencia de que el actualizador pudo aplicar su candidato de ensayo sobre la instalación Windows sintética y pasar las comprobaciones locales reportadas.

Los indicadores `updateSucceeded=false`, `portalChecked=false` y `productionAccepted=false` son intencionales para este modo. No hubo comprobación del portal ni aceptación de producción. La revisión r3 recompila el backend actual sin un cambio funcional solicitado; valida el mecanismo de actualización, pero no es una versión de producto para entregar al cliente. Continúan pendientes la revisión independiente, la evaluación formal de cobertura, la ruta de portal autorizada, el cierre de WP-010 y la definición/implementación de los cambios funcionales. TSK-031 a TSK-034 y MS-003 siguen In Progress.

### Identificación del edificio o recinto — 2026-10-20

Se implementa la mejora solicitada: al crear o editar una propiedad, la interfaz pide el nombre del edificio, urbanización o recinto; se persiste como `recinto`, se muestra junto a la propiedad y se incluye en la búsqueda. La API rechaza el alta o edición si falta ese valor. La interfaz y el backend identifican el contrato `propiedades-v2`, sin declarar compatible la versión anterior. Verificaciones locales: 12 tests Rust, 6 tests unitarios Node, 4 tests de navegador del actualizador y build de frontend satisfactorios. La publicación de los assets y la entrega de actualización para cliente siguen pendientes de pruebas de integración con portal autorizado y de aceptación del cliente.

### Modelo corregido: edificios con viviendas agrupadas — 2026-10-20

La aclaración posterior del usuario establece que el edificio debe ser un registro propio y que las viviendas se añaden dentro de ese edificio. El modelo anterior basado en texto `recinto` queda sustituido: la API `propiedades-v3` expone `edificios`, exige `edificioId` en cada propiedad y la interfaz presenta primero la lista de edificios, seguida de las viviendas del edificio seleccionado. La migración convierte los nombres `recinto` existentes en edificios agrupados y conserva las propiedades. Verificación local: build frontend, pruebas Rust, API sintética y flujo de navegador de creación de edificio/vivienda/inquilino/pago; todavía no constituye aceptación del actualizador en Windows ni del portal publicado.
